# Qwen3.8-27B on B70 — 200k context and quality notes — 2026-08-30

Measured on `inference-host` (Intel Arc Pro B70, 32 GB, `xe`). Live
`~/inference/launchers/start-qwen38.sh` was **not** changed. Harbor/Pi eval
stays **98,304 / 32,768**.

## Authority

- Live Qwen cell remains GPTQ-Int4 + BF16 MTP draft + MTP-4 + FP8 KV,
  `--max-model-len 131072`, `--gpu-memory-utilization 0.88`,
  `--max-num-seqs 64`, `--language-model-only`, prefix cache on.
- This document records a **disposable C1 200k** profile that booted and
  completed a filled request. It is not the live default.
- Draft-INT4 is still quality-rejected (P0 ~8k bonus-accept). Do not
  revive it for this ceiling.

| Quantity | Value | Source |
| --- | --- | --- |
| Physical VRAM | 32.000 GiB | `xe` dmesg `VISIBLE VRAM` |
| Usable excluding stolen | 31.891 GiB | stolen **112 MiB** |

| Weights (GPTQ-4 + BF16 MTP) | **17.38 GiB** | `Model loading took` |
| Display outputs | all DP/HDMI **disconnected** | `/sys/class/drm/card0-*/status` |
| kwin_wayland unique Xe VRAM | **~20 MiB** | `/proc/<pid>/fdinfo` `drm-total-vram0` |
| Host RAM | 31 GiB | `free` |
| `/dev/shm` | 16 GiB tmpfs | `df -h /dev/shm` |

A GUI-less boot target is **not** a VRAM lever here. The greeter is a
headless Plasma session with no scanout.

What *did* matter:

1. **`power/control=auto`** let the dGPU runtime-suspend. After idle we
   saw `runtime_status=error`, `runtime resume failed (-ETIMEDOUT)`,
   forcewake MMIO `0xFFFFFFFF`, and `torch.xpu.device_count() == 0`
   even with `--privileged`. Recovery was reboot, then
   `echo on > /sys/class/drm/card0/device/power/control`.
2. **Stale KV-offload shm.** `--kv-offloading-size 8` leaves
   `/dev/shm/vllm_offload_*.mmap` (~8.6 GiB) after `docker rm`. The
   next 200k boot then failed with `Insufficient space in /dev/shm:
   8177 MiB required, 7828 MiB free`. Always `rm -f
   /dev/shm/vllm_offload_*.mmap` on stop.

Persist `power/control=on` (udev) is recommended and **not yet
applied**. Do not treat `multi-user.target` as a memory optimization.

Live launcher (unchanged):

```text
--max-model-len 131072
--gpu-memory-utilization 0.88
--max-num-seqs 64
--kv-cache-dtype fp8
--enable-prefix-caching --mamba-cache-mode align
--kv-offloading-backend native --kv-offloading-size 8
--language-model-only
MTP-4, BF16 draft, GPTQ-Int4 G128
```

Disposable 200k C1 cell that actually served a long request:

```text
--max-model-len 200000
--gpu-memory-utilization 0.95
--max-num-seqs 1
(same image, weights, MTP-4, FP8 KV, prefix cache, 8 GiB CPU offload)
```

Pinned image:
`vllm/vllm-openai-xpu@sha256:f01e24f6c7ff01f1e0662234255a1372297d1dbd89d003cf13c8fad3eab1ba4f`

Weights:
`SergiioB/Qwen3.8-27B-GPTQ-Int4-sym-G128-MTP-BF16` (host copy under
`/home/mike/inference/models/`).

`max-num-seqs 64` and a 200k single request **cannot share** this pool.
Moving live to 200k is a serving-shape change, not a flag tweak.

Prefix cache does **not** grow HBM. It reuses GPU pages (plus CPU/SSD
tiers for *completed* prefixes). A 200k *active* request still needs
~200k tokens of GPU KV. Cold 200k prefill is rare in agent traffic;
the reservation is not.

| u088-l160k | 160000 | 0.88 | 5.65 GiB | refuse; same 143,104 |

| **u095-l200k** | **200000** | **0.95** | **7.77 GiB** | **health ok; 207,194 tokens; 1.04× for 200k** |

At 0.95 C1 the engine also logged:

- peak activation **2.86 GiB**
- graphs **0.15 GiB** (C1; earlier cap-64 research overlays were much larger)
- suggest `--kv-cache-memory=8536633344` (7.95 GiB) to fully use the card

So live **0.88 is already the single-request ceiling (~143k)**. 145k
does not fit without raising utilization.

## Filled completion (not just health)

Script: [`scripts/qwen38-200k-fill.sh`](../scripts/qwen38-200k-fill.sh).
Receipts:
`~/b70-evals/qwen38-b70-gptq-int4-mtp4/20260830T060427Z-200k-fill/`.

Method: calibrate 200 vs 400 repeats of `The quick brown fox jumps over
the lazy dog. ` on `/v1/chat/completions` (10 tokens/unit, 52-token
template overhead), then send **19,594** units targeting 196,000 prompt
tokens, `max_tokens=32`, `temperature=0`, `seed=12345`.

| | |
| --- | ---: |
| HTTP | 200 |
| Prompt tokens | **195,992** |
| Completion tokens | **32** |
| Total | 196,024 / 200,000 |
| `finish_reason` | `length` (hit `max_tokens`) |
| Wall | **355.669 s** (~551 prompt-tok/s e2e) |
| GPU KV | 7.77 GiB / 207,194 tokens |

The model returned coherent text (it described the repeated pangram and
said there was no question). First fill attempt failed on the leftover
shm mmap above; the numbers here are the second run (`FILL_OK`).

This is a **pad prompt**, not Harbor. It proves the 200k cell can
prefill ~196k and decode 32 tokens without OOM or empty output. It does
not re-run the 98k eval contract.

## Quality / SOTA notes (2026-08-30)

Keep the current **vLLM-XPU GPTQ-Int4 G128 + BF16 MTP + FP8 KV** path
for this card. Higher-bit formats that do not boot with 98k–200k are
not a quality upgrade here.

| Technique | B70? | Notes |
| --- | --- | --- |
| GPTQ-Int4 G128, BF16 MTP draft, MTP-4, FP8 KV | **Keep** | Only proven hybrid-GDN path on Xe2 |
| Draft-INT4 overlay | **Park** | Faster; changes committed tokens (P0) |
| Official Qwen FP8 (~30–31 GB weights) | **Park / boot-test only** | Qwen claims near-BF16; too tight with useful KV |
| GGUF Q5/Q6 (Unsloth / imatrix) | **Experiment only** | Better bits, worse GDN/MTP engine on this host |
| EXL3 / ExLlamaV3 | **NVIDIA-only** | Official [turboderp/Qwen3.8-27B-exl3](https://huggingface.co/turboderp/Qwen3.8-27B-exl3) exists (2–6 bpw, self-calibrated). CUDA 12.4+ / TabbyAPI. No XPU backend. |
| NVFP4 / SGLang CUDA cookbooks | **NVIDIA-only** | Blackwell / L40 / 5090. Not valid on Intel XPU |
| OpenVINO INT4 | Glance | No B70 long-context evidence |

Highest quality on this 32 GB card is still **keep the verifier
honest**: BF16 draft, thinking/sampling as Qwen specifies, FP8 KV as
the tax for 98k–200k, do not spend the last gigabytes on fatter
weights. Official thinking sampling is `temp=1.0, top_p=0.95, top_k=20`.
The B70 eval toml currently has `supports_reasoning_effort = false`.

## If we cut live over to 200k later

Required together:

1. `--gpu-memory-utilization 0.95`
2. `--max-model-len 200000` (or 196608)
3. `--max-num-seqs 1`
4. `echo on > …/power/control` before start
5. `rm -f /dev/shm/vllm_offload_*.mmap` on stop
6. A filled soak like `scripts/qwen38-200k-fill.sh` after any image bump

Do **not** raise max-model-len at 0.88. Do **not** keep 64-way
concurrency at 200k.
