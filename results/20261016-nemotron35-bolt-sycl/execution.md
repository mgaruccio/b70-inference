## Real API cells

Launched via SSH into host Bash; each controller was protected with `nohup`, stdin `/dev/null`, log redirection, recorded PID and an SSH parent `wait` returning its exit status. Each cell uses a separate output directory, creates a stopped Bolt container while Qwen is still serving, stops Qwen, starts Bolt exclusively on localhost port 18098, then removes Bolt and restores Qwen. Exact container argv and frozen controller are in each cell. Qwen canary uses `/v1/completions`, exact 7+1 token usage and finite logprobs; raw responses retained.

```bash
python3 -B run-cell.py --name smoke-01 --context 2048 --batch 512 --ubatch 128 --bench
python3 -B run-cell.py --name smoke-02 --context 2048 --batch 512 --ubatch 128 --bench
python3 -B run-cell.py --name ctx64k-ub128 --context 65536 --batch 512 --ubatch 128 --bench --long-bench
python3 -B run-cell.py --name ctx64k-ub512 --context 65536 --batch 512 --ubatch 512 --bench --long-bench
```

The first cell failed on an obsolete argument; later cells use `--load-mode none`. Text-only, one sequence, q8_0 KV, flash attention on, no speculation, embedded Jinja template with thinking disabled, greedy temperature 0. Correctness requests stop naturally; timing requests force 128 output tokens with EOS ignored. Cache reuse is disabled and actual `timings.cache_n == 0` is required. Short prompts use 55 input tokens. Long timing prompts are 8,270 input tokens; actual served tokenization/detokenization constructs the filler, and response usage establishes the rendered count. Exact code retrieval uses 8,238 input tokens.

Results are medians of **three** measured requests after one warmup, not peak/cherry-picked numbers. Client decode = `(completion_tokens - 1) / (elapsed - first_content_time)`; server timings retained separately. First-token latency is measured to the first nonempty streamed content. Prefix-cache cold does not mean filesystem/model cold; model loading and compilation are excluded.

### Initial results

- `smoke-02`: READY, 17×19→323, and Python `add` all pass. 2,048 configured context, short decode **28.5603 tok/s**, median TTFT **0.62947 s**. This was compatibility-only, not a usable context limit or tuning baseline.
- `ctx64k-ub128`: all three smoke checks pass; exact `BOLT-7319-CEDAR` retrieval passes at 8,238 tokens. Short decode **28.5166 tok/s**, median TTFT **0.62536 s**. Cold 8,270-token decode **27.9124 tok/s**, median TTFT **22.0381 s**, median server prefill **377.0226 tok/s**.
- Device evidence in the verbose 64K log: 89/89 layers offloaded to SYCL0, 20,446.77 MiB GPU model buffer, 544 MiB host model buffer, 272.01 MiB KV, 164.69 MiB recurrent state (F32), and 94.08 MiB reserved GPU compute buffer. These are reported buffer sizes, **not measured peak VRAM**.
- `ctx64k-ub512`: all smoke/anchor checks pass. Short decode **28.5561 tok/s**; long decode **27.9169 tok/s**. Cold 8,270-token median TTFT **10.7940 s**, median server prefill **796.6502 tok/s**: about **2.11× prefill throughput / 51.0% lower TTFT** than microbatch 128. Single-token decode is effectively unchanged. Longer generated text differs in all three corresponding short and long A/B requests; input JSON matches exactly. This is not a bit-identical result or a general quality-regression assessment. Repeated same-config checks are next.
- `ctx64k-ub512-repeat`: second independent launch passes all smoke/anchor checks and repeats **796.8350 tok/s** median cold prefill, **10.7383 s** TTFT, **27.9033 tok/s** long decode. Three **identical** short request JSONs (same prompt, seed 42, temperature 0, cache disabled) produce three distinct coherent continuations. Same-config output variability exists; the first A/B mismatch cannot be attributed solely to microbatch changes. No bit-determinism claim. Original Qwen restored.
- `ctx64k-b1024-ub1024`: logical batch and physical microbatch both raised to 1,024. Smoke and exact 8K retrieval pass. Short decode **28.56145 tok/s**, long decode **27.94523 tok/s**, cold prefill **949.2903 tok/s**, long TTFT **8.84306 s**. This is a bundled batch-limit change, not evidence attributing the gain to physical microbatch alone. Reserved GPU compute buffer rises to 360.72 MiB; host compute buffer 192.11 MiB. Still no measured peak-VRAM claim.
- `b1024-esimd1-quality`: explicit default ESIMD=1 reproduces **948.9884 tok/s** cold prefill, **8.80646 s** long TTFT, **28.55476 tok/s** short and **27.89314 tok/s** long decode. ## Observed failures / limitations

- Initial build failed because the development image no longer includes oneDNN. Mounted the already-installed GPU oneDNN read-only; rebuild passed. No driver/runtime installation on the host.
- The completed download verified both exact size and SHA256, but its shell epilogue exited 127 (`lama-server: command not found`): the lead overwrote `prepare.sh` while the download invocation still had it open, shifting the subsequent script read. This was a script-execution mistake, not a corrupt download. Preserve initial script and log; do not overwrite scripts with in-flight invocations.
- First Bolt cell: `--no-mmap` is no longer accepted; exited before model loading. Original Qwen restored and canary passed. Correct source-supported replacement is `--load-mode none`.
- No-GPU argument precheck with `-ngl` cannot finish because SYCL GPU enumeration fails without device access. Dependency check passes, but do not call that argument precheck a pass. Corrected real GPU cell passed.
- Experimental prototype build orchestration first failed locally because the background runner used Fish to parse a Bash heredoc; no host compilation occurred. A frozen host Bash script fixed the wrapper. Its first container retry then failed at CMake because the fresh development image lacked Ninja—the successful baseline had installed prerequisites inside its now-removed build container. Revision-2 build scripts recreate exactly those transient prerequisites (`ninja-build`, `libcurl4-openssl-dev`, `pkg-config`), without installing anything on the host/production image. Neither error is a kernel numerical failure.
- Lab preview/show-patch failed ENOENT; native text review used. First artifact `scp` attempt used brace expansion incompatible with SFTP scp; bounded SSH tar retrieval succeeded. A `grep | head` inspection returned SIGPIPE under pipefail after artifacts had already retrieved successfully.
- SYCL command graphs default off; pinned source rejects `MUL_MAT_ID` capture. Runtime `graphs reused` log counters are graph-structure reuse, not proof of SYCL command-graph execution. Do not force graph capture based on those counters.
- Native model context is 262,144; 65,536 configured so far, with actual prompts tested only through 8,270 tokens. No native/max-context correctness claim. No multimodal, tool-calling, thinking-enabled, concurrent-serving or speculative validation yet.
- Open B70 issue #29183 concerned other quant/model configurations and a hypothesized DeltaNet mechanism; it was a reason to test, not evidence this Mamba-2 checkpoint must fail. The completed >8K checks passed.

## Continuing optimization, not promoted

The NVFP4 Mamba projections are the next kernel/format target: 2.29614 GiB of weights, roughly half of the estimated active weight reads per decoded token. Comparing estimated traffic with nominal peak bandwidth does **not** establish whether memory, kernels or host launch/serialization dominates; no per-operation timing has been collected. The isolated native reorder-GEMV artifact was statically reviewed without blocking findings and integrated as `6fcebbfb`. Its SYCL build, dependency/version precheck, 112 native numerical cases and API guards passed; the first measured decode gain is recorded above. An independent repeat confirmed the decode gain; integer-format comparisons continue. Read-only investigation is checking whether proper BF16 prefill can replace the current F32 fallback without weakening numerical gates; no such implementation or speed claim yet.

The user requested integer-format investigation and then authorized necessary cleanup without further prompts. Selective NVFP4 `ssm_in`/`ssm_out` conversion—**80 tensors across 40 layers**, not the MoE experts—adds 2.04102 GiB for Q8_0 or 1.05240 GiB for Q6_K. Neither recovers information lost in the original quantization. Original models remain intact. The two specifically approved unused benchmark images were removed; user subsequently approved normal unmount/removal of the obsolete KV-offload backing image. This freed about 48 GiB. Stock conversion support and the unnecessary copied-IQ2 imatrix guard were source-verified. Exact 843-entry anchored type maps were generated using upstream GGUFReader and installed NumPy in a CPU-only container; only the 80 NVFP4 projections are selected. See `requantization.md` for the defined native CLI negative/positive tests, guard patch, numerical/payload checks and API process. The pristine dry-run confirmed exactly 80 intended conversions and the spurious imatrix warning. Its tokenizer preview contained one invalid UTF-8 byte; raw logs remain intact and parsing now uses replacement decoding only for log text. The corrected pipeline verified the Q8 artifact, all 763 untouched payloads and zero metadata changes; its API check subsequently passed 19/20, failing the gate as recorded above. Q6_K likewise passed artifact verification but not the model gate. The original-weight native kernel remains the accepted development candidate; see `requantization.md` for both artifacts and subsequent Q8 scratch cleanup.

Conversion guards: `--tensor-type` is a regex search, so require anchored names and inspect the complete dry-run type map. A global output type can affect nonmatching tensors; `COPY` disables conversion entirely. Do not assume a global IQ2_XXS setting preserves existing Q8 tensors. Require identical names/shapes and byte-identical payloads for every non-target tensor, not a byte-identical GGUF file: the quantizer rewrites type/version metadata and converted tensor offsets/types. Validate chat template and loader behavior too.

UR inspection is retained in `preparation/ur-runtime-inspection.log`: installed oneAPI2026.0 has legacy/v2 UR0.12.0 libraries, both loaded by a no-device trace. This does not identify the active GPU adapter or establish its default queue mode. No UR knob was applied.
