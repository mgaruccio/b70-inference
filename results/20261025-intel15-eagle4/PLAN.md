# Intel 1.5 / Qwen3.8-27B: native MTP versus EAGLE-4

Status: bounded engineering comparison completed; see [REPORT.md](REPORT.md) for results and limitations. Native MTP was measured at the published 0.8 memory fraction and the approved 0.9 control; EAGLE was measured at 0.9 after failing to fit 0.8. Native cache tests, public streaming, and simple semantic canaries passed, but exact greedy equivalence remains unproven and this EAGLE port is much slower on the tested workloads. The original ten-repeat paired protocol below was not completed: after the observed long runtimes and the user's delegation of that decision, the final EAGLE CLI cell was bounded to one measured request. This is development / engineering evidence, not a standard-publishable benchmark.

Baseline startup required a read-only `/dev/dri/by-path` bind mount for oneCCL; both launchers use the same mount without changing runtime code or privileges. The native-MTP arm uses the legacy runner and internally expands the requested block size 64 to 1024. Its observed model-plus-MTP footprint was 18.04 GiB, with 3.83 GiB available for KV and 83,636-token KV capacity. Preserve these actual runtime values when comparing the EAGLE V2 arm. Baseline smoke artifacts are retained under `/home/mike/b70-evals/20261025-intel15-eagle4/native-mtp-by-path/` on the host and `/tmp/intel15-eagle4-comparison/native-mtp-by-path/` on the coordinator; smoke timings are not final paired performance results.

Ordinary-target references (`ordinary-reference/probe/results.json`) completed all requests successfully. At 32K input tokens, all ten 512-token outputs match each other and the native-MTP smoke output exactly. At 8K, the ordinary target produced nine distinct sequences across ten identical greedy/seed-0 requests; divergence from repeat 0 starts as early as token index 3. Native MTP also diverges from that reference at index 3. This is baseline nondeterminism, not evidence establishing an EAGLE defect or permission to ignore candidate differences.

EAGLE initial startup (`eagle-initial/server.log`) loaded target plus draft in 21.29 GiB, selected target block size 1024, and reported 2.32 GiB available for KV. At the published 0.8 memory fraction, the engine rejected max length 40000 because its computed requirement was 5.25 GiB (estimated maximum length 5184). The follow-up diagnostic (`eagle-cache-diagnostic/server.log`) confirmed correct window/precision isolation and enabled hybrid caching: 48 Mamba groups require 1536 MiB, 16 full-attention target groups require 1280 MiB, and the draft SlidingWindowSpec(window=4096, block_size=16, FP16) requires 2562 MiB after padding every physical page to 2 MiB. Total: 5378 MiB. The diagnostic preserved the admission check and failed as expected; it is not performance evidence.

The published 80% MTP baseline and additional 90% MTP control were retained; EAGLE was tested at 90%. The launchers still default to 0.8; 0.9 requires an explicit argument. No block-64 draft-kernel adaptation was introduced. The first 90% EAGLE attempt passed allocation with 5.51 GiB available KV and 41,978-token capacity but failed warmup because Intel InputBatch lacks `has_prefill`. Run short arithmetic, code, and structured-output canaries plus an excluded warmup before measured requests.
4. Retain a deterministic request set, exact rendered prompt tokens, greedy sampling with seed 0, output cap 512, ignored EOS, no prefix reuse, and concurrency 1. Exercise 8K and 32K input classes supported by the declared 40000-token envelope. Retain the same request bytes for every arm. Validate each response's output length, token IDs where exposed, text, finish reason, and metric accounting.
5. Establish ordinary-target output references on the same Intel image/checkpoint/precision with speculation disabled. Repeat reference requests to expose runtime nondeterminism rather than treating it as candidate error or concealing it. Compare MTP and EAGLE outputs against those references, including first divergence and full-output match rate. Investigate failed gates before performance promotion.
6. Run paired native-MTP / EAGLE-4 / EAGLE-4 / native-MTP cells, with identical warmup and ten measured requests per workload per cell. Each cell uses a fresh temporary server. Save failures, retries, and all measurements; no cherry-picking.
7. Also run Intel's documented `vllm bench serve` public-boundary probe with fixed seed, 32768 input tokens, 512 output tokens, random-range-ratio 0, concurrency 1, ignored EOS, and temperature 0. 8. Report medians and dispersion for post-first-token decode, TTFT, full request latency, accepted/proposed tokens, draft rounds, accepted tokens per round, and exposed depth metrics. Report target/drafter memory, KV capacity, and the actually tested context limit. 9. Retain launch files, source modifications, environment output, client commands, requests/responses/token IDs, metrics, server/kernel logs, benchmark JSON, and cleanup outcomes in a dedicated run directory. Do not distribute raw secrets or package draft weights into the report.
10. Stop and remove owned temporary containers/listeners after each cell; preserve artifacts and verify the disk-space floor. No persistent deployment changes.

## Integration gates

Inspect the actual Intel-patched vLLM 0.26 source and native FP8 ABI before implementation. Establish scale direction/granularity/storage, target and draft cache allocation/grouping, quantized writes and reads, accepted-row compaction, ordinary fallback, GDN state precision, and graph/eager lifecycle. FP8 bytes must never be interpreted as unscaled FP16 values. Keep unsupported shapes fail-closed.

Use focused CPU/interpreter tests, native XPU cache/scale/compaction tests, and the real HTTP journey above. Unit tests and a mock runtime do not substitute for the public-boundary run. Do not claim an existing qualified kernel launch remains active if the new runtime chooses a different layout.

Intel's E4M3 E-SIMD decoder explicitly collapses subnormal bytes to signed zero (`custom-esimd-kernels-vllm/csrc/eagle/page.attn.fp8.h:45-52`), whereas a standard FP8 Triton conversion retains subnormals. Test this on the native GPU before interpreting token differences. Keep the published baseline unchanged; if EAGLE verification requires different attention arithmetic, record that delta and use a same-arithmetic control to distinguish it from drafter effects. Equal FP8 storage settings alone do not establish equal attention arithmetic.
Source qualification: the pinned official target has 24 query heads / 4 KV heads (GQA ratio 6), while Intel's `flash_attn.py:1043-1047` E-SIMD dispatch admits ratio 2 or multiples of 4. Thus that decoder is not expected to serve this TP1 target through the inspected dispatch. Confirm the actual installed path before attributing any mismatch to subnormal flushing; the source warning alone does not establish that this recipe uses it.

The auxiliary token-ID probe uses `/v1/completions` for fixed token prompts. Its canaries validate protocol and retain answers for manual quality review; a successful probe exit alone is not a semantic-quality pass. Intel's own `vllm bench serve` remains the primary performance measurement.
